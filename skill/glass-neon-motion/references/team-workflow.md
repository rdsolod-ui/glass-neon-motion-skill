# Команда сборки, а не только приёмки

Используй при запросе пользователя на агентов или применимых project-инструкциях. Роли ниже переносимы между проектами; пути и число параллельных исполнителей назначает координатор по текущему стеку. Наличие Markdown не запускает агентов.

## Разделение функций

| Роль | Делает | Передаёт | Не совмещать в одном проходе |
|---|---|---|---|
| Material/design lead | Источники, композиция, specimen/reading токены | Brief, карта наблюдений, приёмочные кадры | Авторство всех production-файлов |
| Site builder | Рабочие страницы и интерактивные состояния | Код, screenshots, реальные проверки | Самоприёмка как независимая |
| Moodboard builder | Атлас, визуальные образцы, каталог рецептов | Coverage-map, source links, working board | Перезапись CSS другого исполнителя |
| Skill maintainer | Переносимые рецепты, зависимости, инструкции | Skill и validator result | Обещания непроверенного runtime |
| Motion/accessibility QA | Независимый браузерный review | Findings с steps/evidence и recheck | Исправления чужих файлов без handoff |
| Integration/release | Общие файлы, build, CI, release/read-back | Commit/URL/verification | Публикация без разрешения |

## Порядок запуска

1. Координатор читает brief, снимает baseline и назначает каждому исполнителю непересекающиеся файлы. Shared tokens/CSS/lockfile остаются у одного владельца. Запиши выбранные material scenes и критерии до реализации. Раздели 2D film без базового outline/толщины и 3D optical edge с локальными бликами/фаской; не выключай focus-visible.
2. Запусти реальных исполнителей доступным collaboration-инструментом: site, moodboard, skill могут работать параллельно после brief. Не создавай отдельные пользовательские чаты для внутренних подзадач. При ограничении слотов объединяй design и integration у координатора, переиспользуй завершённых исполнителей.
3. При каждом handoff сообщи `files | decisions | checks | findings | evidence | unverified`. Не редактируй файл, пока его прежний владелец продолжает запись. Изменение общего контракта отправь всем зависимым ролям.
4. После static pass отдельно проверь сайт и мудборд: цвета/материал/композицию до дальнейшего motion. Если один исполнитель проверяет другого, он не редактирует его artifact; это peer review. При сложных interaction bugs выдели QA-роль.
5. QA проверяет final motion/runtime; исполнитель исправляет замечания, reviewer повторяет затронутые сценарии. Block означает дефект, который мешает заданному scope; непроверенное не превращай в Approve. Приёмка пользователем и технический reviewer verdict различаются.
6. Интегратор проверяет build и diff, публикует только разрешённые изменения, получает live read-back. Сохранённая роль, её native discovery, фактический запуск, выполненный review и опубликованная версия — пять разных состояний.

## Задание исполнителю

Передавай: цель и user brief; role; exact owned files; read-only dependencies; visual criteria; необходимые сценарии; output report path; ограничения publication. Задание reviewer содержит артефакт и критерии, но не готовый положительный вердикт. Не выдавай выводы автора за независимый запуск.

## Для текущего LUMA

Проект содержит native `.codex/agents/*.toml`, ownership manifest и AGENTS.md. При недоступном role selector текущего инструмента загрузи соответствующий TOML, передай его инструкции обычному дочернему агенту и явно отметь этот способ. Не меняй глобальный конфиг и не перезапускай Codex ради discovery.
